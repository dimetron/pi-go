### Functiontype `tool.Context` references in `functiontool.New` handler types

The v1.4.0 `functiontool.Func` is `func(tool.Context, TArgs) (TResults, error)`.
The v2.0.0 `functiontool.Func` is `func(agent.Context, TArgs) (TResults, error)`.
Every `newTool(…)` literal that names the parameter as `ctx agent.ToolContext`
must be retyped to `ctx agent.Context`. Same set of files as above
(`internal/tools/*.go` + `internal/palace/tool_*.go`).

## 3. `agent.NewRunner` / `runner.New` — import path only

`internal/agent/agent.go` has:

```go
import "google.golang.org/adk/runner"
// ...
runner.New(runner.Config{ … })
```

The new path is `google.golang.org/adk/v2/runner`. Public API of `runner.New`
is unchanged. No other source-level changes needed in this file beyond
the import path and the `runner.Config{…}` struct literal (which is
backward-compatible — the new struct adds fields but doesn't remove any).

## 5. Hand-rolled mocks that need method additions

The v2.0.0 `agent.Context` interface is a **superset** of the v1.4.0
`agent.ToolContext` interface (it adds the workflow / dynamic-orchestration
methods listed in `v2-api-delta.md §5.1`). So our `mockToolCtx` types
that assert `var _ agent.ToolContext = (*Y)(nil)` will need to be
upgraded to satisfy the new surface — either by:

- Re-asserting against `agent.Context` and adding the new methods; or
- Keeping the assertion against `agent.ToolContext` (which still exists
  in v2.0.0) — in which case no method additions are required.

Per A1, we want `agent.Context` compliance. Per A5, we add the full v2
guide-recommended method set.

```

```

Three `var _ agent.ToolContext = ...` assertions and one
`var _ agent.CallbackContext = ...` assertion. Each must either:

- (a) Stay as `agent.ToolContext` and have no new methods added to the mock
  (works, because v1.4's `ToolContext` interface is preserved in v2.0.0
  as a valid sub-interface of the new `agent.Context`); or
- (b) Upgrade to `var _ agent.Context = ...` and have the new method
  set added to the mock.

Per A1/A5, we choose **(b)**. Each of the four assertions becomes
`var _ agent.Context = ...` and the corresponding mock struct grows the
new method set.

## 9. Open questions deferred to design

1. The pre-existing `TestCommitCommand_ConfirmCommits` failure on trunk
   is unrelated to ADK. Should the migration gate be:
   - (a) Run `go test ./...` and accept the failure (because it was
     failing on the parent commit too); or
   - (b) Skip the failing test during the gate via `-run` filter or
     `-short` tag; or
   - (c) Fix the test as part of the migration PR.

   Default: (a). The migration is responsible for "doesn't make it
   worse", not for "fixes everything that was already broken".

   beyond the four `var _ agent.ToolContext = ...` ones) need the three

   during the design slice.
