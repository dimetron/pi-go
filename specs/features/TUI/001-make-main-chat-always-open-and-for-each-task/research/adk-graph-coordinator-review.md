# Review: ADK Graph Coordinator Research and Candidates A/B/C

## Summary

The research identifies a real ADK v2 task-delegation mechanism, but overstates its fit: it is a sequential, in-process `LlmAgent` protocol, not an enforced per-prompt router or a background-task scheduler. A is the only near-term implementable option, provided it explicitly specifies queued-message rendering, slash-command policy, title semantics, and cancellation. B needs a proof-of-concept and a different external-process bridge. C addresses the right product gap but is currently an incomplete second orchestration system with invalid API sketches. The documents do not yet make a defensible single choice obvious; ship a bounded A, then choose B versus C from an explicit product decision on in-process ADK agents versus durable external jobs.

## Design A critique

- **Feasible, but incomplete.** The one-active-loop model is real: `submitPrompt` creates one channel and sets `running` ([internal/tui/agent_loop.go:338](../../../../internal/tui/agent_loop.go:338)); completion clears it ([internal/tui/agent_loop.go:801](../../../../internal/tui/agent_loop.go:801)). FIFO handoff from `handleAgentDone` is a small, low-risk change.
- **Citation error:** A repeats the incorrect `tui.go:884-887`; the guard is `:888-890`.
- **Internal inconsistency:** “Only the first sets the session title” (`A:31-32`) is not current behavior: every `submitPrompt` calls `applySessionTitle` ([internal/tui/agent_loop.go:332-336](../../../../internal/tui/agent_loop.go:332)). State the intended rule and its stored flag.
- **Missing interaction policy:** removing only the `running` lock enables not just typing but `/clear`, `/exit`, history/search, model changes, and other input handlers. `InputSubmitMsg` routes slash commands before prompts ([internal/tui/tui.go:543-549](../../../../internal/tui/tui.go:543)). Define which are permitted while a turn runs and whether queued user messages appear immediately or only on dispatch.
- **Missing lifecycle details:** retain queued text+mentions, queue limit/backpressure, duplicate/history behavior, Ctrl+C semantics (cancel active only vs clear queue), session switch/restart behavior, and rendering/cursor changes in both TUI views. “Agent nil no-op” is underspecified: advancing a queue in tests should not silently drop it.
- **Specificity:** the proposed `drainNextQueued() (tea.Model, tea.Cmd)` is plausible, but it omits where slash commands are handled and how message placeholders map to queue entries. The pros/cons are fair; its stated weak fit for mandatory delegation is accurate.

## Design B critique

- **Fundamental mismatch:** B calls delegation “enforced” (`B:30-33, 96-99`), but task mode merely exposes a task tool. The chat LLM can finish without delegating; a system prompt is not enforcement.
- **B1 sketch is not implementable as written.** `Mode` exists only on `llmagent.Config`, and the root detects task children only when they are `llminternal.Agent`/`LlmAgent` ([llmagent.go:146-175](../../../../../../../../Users/dimetron/go/pkg/mod/google.golang.org/adk/v2@v2.0.0/agent/llmagent/llmagent.go:146)). The shown `TaskSubAgent.Run(ctx agent.Context, input any)` has the wrong `Agent.Run` signature (`Run(agent.InvocationContext) iter.Seq2[...]`) and cannot implement `agent.Agent` externally because that interface has an unexported method ([agent/agent.go:34-48](../../../../../../../../Users/dimetron/go/pkg/mod/google.golang.org/adk/v2@v2.0.0/agent/agent.go:34)). A viable experiment would instead be a task-mode `LlmAgent` whose tool calls an external-spawner adapter, then calls `finish_task`; that adds an LLM round and does not directly stream a process as an ADK task agent.
- **Long-running claim is false for the supplied architecture:** the coordinator waits during `RunNode`; on interruption it ends the `runner.Run` and needs a later reply to resume. It cannot “take the next queued task while one is in flight” (`B:108-110`). B also omits the TUI queue required by its own acceptance criterion `B:84-85`.
- **Missing work:** deterministic routing contract, external event-to-ADK-event mapping, task cancellation/timeouts, process result schema, task/session IDs and persistence, sidebar `/agents` compatibility, and event ordering/partial-stream rendering. Concurrent `Runner.Run` calls on one session must be proven, not assumed.
- **Trade-off framing:** B is marketed as native and exact while its hardest bridge is invalid. B2 is a distinct in-process rewrite, not a small alternative to B1; compare its tool/sandbox/credential and failure-isolation consequences explicitly.

## Design C critique

- **Best product direction for independent external jobs, but not yet a design.** It overlaps A for queued input and B1 for external delegation, while adding a durable task identity/control plane.
- **Incorrect ACP claim at `C:20-21`:** `claudecode.RunRequest` has `SessionID`, but the current shared flow always calls `NewSession` and prompts that new ID ([internal/acp/client/session.go:158-183](../../../../internal/acp/client/session.go:158)); `internal/subagent/spawner_acp.go:116-120` does not pass a session ID. “Resume of a completed session” is unsupported today.
- **Invalid/inaccessible signatures:** `context` must be `context.Context`; `subagent.AgentResult` does not exist (the result type cited is `tools.AgentResult`); `taskHandle` is undefined. `Orchestrator.SpawnWithInput` exposes only an event channel plus agent ID, not a `*Process` or ACP `RunningSession`, so C cannot retain the advertised live handles without a new exported lifecycle API ([internal/subagent/orchestrator.go:694](../../../../internal/subagent/orchestrator.go:694)). `Process` is the common wrapper, including ACP, and only exposes `Events`, `Wait`, and `Cancel` ([internal/subagent/spawner.go:50-78](../../../../internal/subagent/spawner.go:50)).
- **Contradictory scheduling:** desired state says FIFO and either serial or parallel “per policy” (`C:26-32`); acceptance says a new task starts “or waits” and up to pool size run concurrently (`C:84-89`). Choose one v1 policy and define completion/order semantics. The existing pool is private to `Orchestrator`; C cannot read its size without an API.
- **Missing core protocol:** who chooses agent and how (not the main LLM if every prompt is forcibly dispatched); when/where the main LLM receives a completed task result; task record persistence/recovery/adoption after restart; bounded event buffering; synchronization around `active`/`results`; cancellation ownership; worktree merge semantics; and task-specific sidebar/chat rendering. “Results are in session/JSONL once written” is an unproven persistence promise, not a current TaskManager behavior.
- **Trade-offs:** process isolation and correlation are genuine advantages. “Natural home for ACP steering” is only partially true: retaining a wrapper handle is insufficient until the ACP client supports another prompt on an open connection.

## Cross-design comparison

- The research recommendation (A first, then evaluate task mode) aligns with A's low risk and B's architectural gap. It conflicts with B's claim that it can run another queued task while a task is in flight, and understates C as the more natural external-process path.
- A, B, and C are distinct in primary control plane: A serializes root turns; B delegates inside one ADK run; C schedules independent external jobs. A is also a prerequisite UI capability for B and C, so the set is not mutually exclusive.
- Before selecting B or C, decide: (1) must each task be an independent, cancellable external job? (2) must a task's result re-enter the main ADK conversation automatically? (3) is concurrent task execution required in v1? (4) must tasks survive restart? (5) which agent kinds must be supported? B fits only an in-process LLM-agent model unless a new bridge is proven; C fits external jobs but needs a concrete persistence/event contract.

## Recommended follow-ups

1. Revise research to remove `NewBranch`, qualify task-mode guarantees, and correct `tui.go:888`.
2. Write and test A as a bounded FIFO queue with a documented busy-time command/cancellation policy; do not change routing behavior in the same slice.
3. Run a small B spike: a real task-mode `LlmAgent` with a process-launch tool, proving `finish_task`, event forwarding, cancellation, and session isolation. Reject B1 if it requires unsupported custom task agents.
4. If independent background work is a requirement, design C around a new `subagent` task-handle interface plus durable task records before modifying the TUI.
